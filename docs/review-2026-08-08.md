# Hoglah — functional and code review

**Date:** 2026-08-08 · **Reviewed:** `master` @ `87003b3`, source version 0.10.2
**Method:** the product was exercised end to end (CLI, library, web monitor; stub
adapter and a real Ollama), then the source was read. Every claim below is backed
by a run or a probe, reproduced inline.

> **Follow-up (0.10.3 + 0.10.4):** all review items actioned.
> 0.10.3: H1–H4, F1–F4/F6, M1–M2/M5/M7–M8, packaging pins.
> 0.10.4: F2 metrics exporter on `hoglah run`, F5 CI services, M3–M4 fairness

## Part 1 — Functional review

**Baseline:** `162 passed, 18 skipped` locally.

### What works

Submit → poll/`wait`, `ps` / `status` / `stats` / `dlq` / `requeue` / `rm` /
`clear`, JSON output, the web monitor (`/`, `/api/summary`, `/api/jobs/{id}`,
400 on an unknown status), real Ollama generate with token counts, idempotent
submit (same key → same id), delayed jobs (stayed `queued`), `depends_on` gating
(child held while the parent was incomplete; correctly failed on a missing
dependency), the retry/backoff path, and the DLQ → requeue round trip.

The lease / heartbeat / reclaim design is well thought through and the SQLite
claim is genuinely atomic. This is a real, working queue.

### Functional defects

#### F1. The real adapter reports false truncation on a normal completion

The README's own quick-start prompt triggers it:

```
$ hoglah submit "Explain context windows in one sentence." --model … --real --wait
[note: truncated, reason=possible_context_truncation_from_model]
```

Stored metadata is self-contradictory:

```json
{"done_reason": "stop", "truncated": true,
 "truncation_reason": "possible_context_truncation_from_model"}
```

Ollama reported that generation ended naturally; Hoglah overrode it.
`adapters.py:290` reads `done_reason` correctly, then applies a fallback
heuristic that flags any output containing the substring `"context"` or
`"truncat"`. Every job that *talks about* context windows is reported as
truncated. The README sells this as a feature ("reports truncation rather than
failing"); as shipped it produces false positives across a whole topic area.

**Fix:** trust `done_reason`; drop the substring fallback, or gate it on
`done_reason` being absent.

#### F2. Four of six Prometheus metric families are structurally always zero

Counters live in a process-local `REGISTRY` (`metrics.py:136`) incremented by the
worker. Both documented read paths are *different processes*: `hoglah metrics` is
a one-shot CLI, and `web.py:198` explicitly builds `Hoglah(start_worker=False)`.

Measured against a queue with 7 jobs, 3 completed:

```
hoglah_jobs{status="completed"} 3          # gauge, from the store — correct
hoglah_jobs_submitted_total 0.0            # always
hoglah_jobs_terminal_total{status="completed"} 0.0
hoglah_job_duration_seconds_count 0
```

The module docstring is honest about process-locality, but the README's
"Prometheus metrics — `hoglah metrics` and `GET /metrics` on the web monitor" is
a claim the topology cannot satisfy.

**Fix:** either expose an exporter from `hoglah run` (where the work happens), or
derive these from the store the way the gauges already are.

#### F3. A permanent error is retried as transient

```
$ hoglah submit "x" --model definitely-not-a-real-model:9q --real --wait
… attempt 2/3 failed: pull model manifest: file does not exist (status code: 500)
… attempt 3/3 failed: …
```

The message contains `500` → `server` → `transient`. The model will never
appear; every retry is guaranteed waste. Root cause in H1 below.

#### F4. CI is currently red, and the rule set is unpinned

`ruff check src tests` — the exact CI command (`.github/workflows/ci.yml:32`) —
fails with two `F401`s in `tests/test_retry_policy.py:7` and `:113`.

`pyproject.toml` has `[tool.ruff]` with **no `select`**, and dev pins
`ruff>=0.4`. Hoglah was missed by the rule-set pinning pass applied across the
other repos, so the rule set also moves under it on any ruff upgrade.

#### F5. Every headline transport is unexecuted in CI

All 18 skips are Mongo, Kafka, RabbitMQ and Redis. CI defines no service
containers, so the four backends/bridges that occupy roughly half the README have
**zero executed test coverage** on any commit. The in-memory fake-transport tests
are valuable, but they never touch `ConfluentKafkaTransport`, `rabbitmq.py`,
`redis_streams.py`, or `MongoJobStore`.

#### F6. Idempotent submit silently discards the new request

Submitting a *different* prompt under an existing key returns the old job with no
warning. Standard idempotency semantics, but for the stated use case ("agent
loops that may retry") a key collision across differing content fails silently.
At minimum, log when the stored request differs from the incoming one.

> Minor: `hoglah --version` printed 0.9.0 against a 0.10.2 source tree — a stale
> editable install in this environment, not a repo bug. Worth knowing because the
> README tells bug reporters to paste `hoglah doctor`, which reports *installed*
> metadata rather than the checkout.

## Part 2 — Code review

### High

#### H1 · `models.py:155-218` — `classify_error` substring-matches an unanchored, caller-influenced string

Error text can embed prompt content and arbitrary model names. Verified false
results in both directions:

| message | classes | retried? | should be |
|---|---|---|---|
| `pull model manifest: file does not exist (status code: 500)` | `{server, transient}` | **yes** | no — permanent |
| `connection reset by peer after 4004 bytes` | `{connection}` | **no** | yes — `"400"` in `"4004"` discarded `transient` |
| `memory layout cannot be allocated` | `{}` | no | `oom` — real Ollama phrasing, matches no pattern |
| `model not found: mushroom-classifier:7b` | `{oom}` | no | `{}` — `"oom"` inside `"mushroom"` |

**Fix:** match structured signals first (exception type, a `status_code`
attribute), then anchor what remains — word boundaries, and `\b[45]\d{2}\b`
rather than `" 500"` / `"500 "`.

#### H2 · `client.py:1575-1583` — `close()` stops the bridge before the worker that feeds it

```python
self._worker_running = False          # signal only — worker then drains for up to 2s
self._message_bridge.stop()           # closes the transport NOW
self._worker_thread.join(timeout=3.0) # jobs finish here and call _deliver → publish_result
```

Every job completing during the shutdown drain publishes to a closed producer.
The outbox prevents loss (it re-emits on restart), but the failure is guaranteed
rather than exceptional, and every clean shutdown leaves an unpublished backlog.

Related: `stop()` drains `_egress_inflight` and then closes, but
`publish_result` spawns a *new* daemon thread per result
(`kafka_bridge.py:504`), so a thread can start after the drain window closes.

**Fix:** stop the worker, join it, *then* stop the bridge.

#### H3 · `kafka_bridge.py:139-141` — a broker message can hijack a client idempotency key; the message is acked with no job and no reply

`idempotency_key` is in `_REQ_FIELDS` and absent from `_RESERVED`, so it passes
through from the message body. Verified:

```
client job id           : 58a340f7-…
bridge enqueue returned : 58a340f7-… (same job)
stored job carries _kafka routing metadata: False -> result can be published back: False
```

`_handle_message` treats the returned id as a successful durable enqueue and
acks. No job runs for that message, and because the pre-existing row has no
`_kafka` metadata, `publish_result` returns early and the outbox scan skips it.
The caller waits on `reply_to` forever.

This is silent message loss in the component whose docstring promises "never
lost, never duplicated."

**Fix:** add `idempotency_key` to `_RESERVED`; and reject an enqueue whose
returned row does not carry the current `correlation_id`.

#### H4 · `kafka_bridge.py:139-157` — type-invalid field values bypass dead-lettering

`JobRequest` is a plain dataclass, so `**extra` accepts anything; the
`except TypeError` only catches signature errors. All four of these were accepted
verbatim from a broker message:

```
retry_policy='not-a-dict'   depends_on='not-a-list'
timeout_seconds='abc'       priority={'nope': 1}
```

`depends_on='not-a-list'` is the worst: `_eval_depends_on` iterates it *by
character*, so the job fails with `dependency n not found`. These are poison
messages that reach the queue instead of the dead-letter destination.

**Fix:** validate field types in `parse_input_message` before constructing the
request.

### Medium

#### M1 · `config.py:320-393` — the dict config path skips validation the env path enforces

```
rejected  model_slots="m=0"        (env string)
ACCEPTED  model_slots={"m": 0}     (dict)
ACCEPTED  tag_rates_per_minute={"t": 0}
```

The scalar fields carry `ge=1` / `gt=0`; the map parsers enforce the same bounds
only on the string branch. Consequence, verified end to end:

```
model_slots={'gemma3:1b': 0} -> job status after 4s: queued
```

`_slot_limit_for_model` returns 0, `_dim_usage(...) >= 0` is always true, so the
job is never reserved — wedged forever, with no error and no log.

**Fix:** move the bounds into the dict branch, or onto the field types.

#### M2 · `client.py:1226-1261` — rate-limit tokens are consumed and never refunded on rollback

The comment says "check all, then charge all", but there is no rollback:

- partial take (1238-1240) — if bucket 2 fails after bucket 1 succeeded, bucket
  1's token is burnt and the job does not start;
- the post-reserve concurrency re-check (1246-1261) calls
  `_release_job_reservation`, which only pops `_inflight_meta` /
  `_inflight_models`.

Under contention the effective rate drifts below the configured rate, silently.

**Fix:** add `_TokenBucket.refund()` and call it on every rejection path that
occurs after charging.

#### M3 · `client.py:1167-1194` — `_dim_usage` runs a full `PROCESSING` scan per dimension, per candidate job, per poll

Each call does `self._store.list(status=PROCESSING, limit=200)` and
JSON-deserialises every row. With fairness on, `poll_limit` jumps to 50, and
`_try_reserve_job` calls it up to `(1 + 1 + len(tags))` times *twice*. Worse,
`_fairness_order` (1148-1158) calls it inside a **sort key**, so `sorted()`
performs DB I/O per element.

Order 400+ full scans per 0.5 s poll for 50 candidates. This activates only when
fairness is enabled — exactly the multi-agent case the feature exists for.

**Fix:** snapshot the PROCESSING set once per poll and pass it down.

#### M4 · `client.py:1181` — the peer count is silently capped at `limit=200`

Past 200 PROCESSING rows the count is an undercount, so every concurrency cap is
exceeded with no signal. Use a `COUNT(*)`-style store query rather than a bounded
`list()`.

#### M5 · `client.py:1065-1087` and `submit()` — no cycle or self-reference detection in `depends_on`

Verified: two jobs each depending on the other sit in `queued` indefinitely,
re-evaluated every 0.5 s forever. No detection, no timeout, no log. Missing and
failed dependencies are handled well; cycles are not handled at all.

#### M6 · `store.py:440-449` — `LIKE` filters interpolate user values as patterns

`tags_json LIKE '%"<tag>"%'` with no escaping. Verified: `tags=["a_c"]` matches a
job tagged `abc`, and `tags=["%"]` matches **every** job. That reaches
`requeue_failed(tags=[...])`.

The `parent_job_id` filter has the same issue and additionally hard-codes
`json.dumps`'s `": "` separator — it would fail silently if serialisation ever
changed.

**Fix:** escape `%` / `_`, or move to `json_each`.

#### M7 · `tracing.py:57-79` — the `MongoClient` is never closed

`JobWitness` has no teardown and `Hoglah.close()` does not touch it, so each
client with `galeed_enabled` leaks a connection pool and its monitor threads. The
CLI constructs a `Hoglah` per command. Same class as the cleanup pass already
applied elsewhere in the estate.

#### M8 · `priority_queue.py` — two documented guarantees do not hold

- The docstring promises tasks sharing a `key` run "serially **in submission
  order (FIFO within a key)**". Ordering is `(priority, seq)`, so a later
  higher-priority task jumps the queue. Verified: submitted A then B, B ran
  first. A caller sequencing a chain by key gets reordering.
- Worker threads are started in `__init__` and there is **no** `close` /
  `shutdown` / `stop`. Every instance permanently leaks its workers, each waking
  on a 1 s timeout forever. For a primitive offered as general-purpose that is an
  API gap. The heap is also unbounded.

#### M9 · `client.py:106-136, 1479` — the SSRF guard does not cover redirects

`_callback_url_allowed` resolves and screens the *initial* host, then
`urllib.request.urlopen` follows redirects with the default handler. A public
endpoint returning `302 → http://169.254.169.254/…` is followed unscreened. There
is also a TOCTOU window between `getaddrinfo` and connect (DNS rebinding).

Low real-world severity for a localhost tool, but the guard exists and is
currently bypassable, which is worse than stating the limit. Install a redirect
handler that re-screens each hop; consider `is_unspecified` / `is_multicast` too.

### Low

#### L1 · `store.py:648-663` — `_closed` is dead code and the docstring overstates it

The flag is written in `__init__` and `close()`, and read only by `close()`'s own
idempotency guard; **no query method checks it**. The docstring claims it "turns
any later call into a clean `ProgrammingError` instead of a use-after-free" —
that error actually comes from sqlite3 itself (verified:
`ProgrammingError: Cannot operate on a closed database`).

The lock-based fix for the #13 segfault is correct and load-bearing; the flag
adds nothing. Either check it at the top of each method, or drop it and correct
the comment.

#### L2 · `tracing.py:198-207` — `except TypeError` is too broad and the warning misleads

It wraps the whole body, so a `TypeError` raised inside galeed (or by
`dict(request.metadata)`) produces "galeed is older than this hoglah — upgrade
galeed", sending an operator after a version problem that is not there. In the
`dict()` case `request_meta` is unbound and the fallback dies with
`UnboundLocalError`, swallowed at line 225.

**Fix:** probe the signature once with `inspect.signature`.

#### L3 · `dispatch.py:49, 96` — `_failed_until` grows without bound

Keys are `(model, backend_idx)`; entries are removed only on a subsequent success
for that pair. A model that never succeeds on a backend leaves a permanent entry,
one per distinct model name tried.

#### L4 · `dispatch.py:83-84` — warm affinity has no spillover threshold

`min(warm or candidates, …)` picks least-loaded *within the warm set*. If one
backend is warm for the hot model, every job for it pins there regardless of
depth, even with idle peers. Defensible (reloads are expensive) but it
contradicts the module docstring's "to balance". A load threshold beyond which a
cold backend is preferred would resolve it.

#### L5 · `client.py:1359-1368` — the FAILED result carries no `timings`

Success writes `finished_at`; failure writes none, so `_age()` in the monitor
shows `-` for every failed job, and failure duration is unavailable to
`observe_seconds` except via the store's `updated_at`.

#### L6 · `tracing.py:113-130` — the 256-entry tracer LRU can evict a live job

Its later lifecycle events then get a fresh `Tracer` with a reset sequence, so
one `trace_id` carries duplicate sequence numbers. Only reachable above 256
interleaved jobs.

## Structural note on the test suite

The three modules with no dedicated test file — `adapters.py`, `config.py`, and
(for these paths) `models.py` — are exactly where H1, M1 and F1 live. Two
specifics:

- `classify_error` *is* tested (`test_retry_policy.py:52-60`), but every case is
  a positive one phrased to match the substring list (`"connection refused"`,
  `"CUDA out of memory"`, `"503 service unavailable"`). No test asks whether a
  match is *wrong*. That is the shape of tests written from the implementation,
  and it is why H1 survived.
- Truncation is tested only through the stub's explicit `num_ctx * 0.9`
  simulation (`test_worker_execution.py:85-119`). The real adapter's
  `"context" in output` heuristic — the one that misfires — is never executed.

## Suggested order

1. **H1, H2, F1** — all three are wrong behaviour on the default path, and each
   is a small, local change.
2. **F4** (pin `select`, fix the two `F401`s) — CI is red now, so everything else
   lands unverified.
3. **H3, H4** — real message loss, but only on transports nothing currently
   tests, which is itself the argument for F5.
4. **M1, M2, M5** — three separate ways a job silently never runs.
5. **F2, M3, M4** — the observability and fairness paths need a design decision,
   not a patch.

Nothing here is architectural: the lease/claim/outbox design is sound, and most
findings are single-function fixes.

The pattern worth naming is that the failures cluster where a **heuristic
substitutes for a structured signal** — substring matching on error text,
substring matching on output text, `LIKE` on JSON — and each one is silent when
it is wrong.
